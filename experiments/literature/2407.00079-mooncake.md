# Mooncake: KVCache-centric Disaggregated Architecture for LLM Serving (arXiv:2407.00079)

**Year / venue:** 2024, ACM TOS, FAST 2025 best paper.
**Headline claim:** Up to 5.25x throughput in long-context simulated scenarios; 75% more requests under real Kimi production workload at SLO.
**Mechanism:** Production architecture (powers Moonshot AI's Kimi). Generalizes DistServe by also disaggregating the *KV cache itself* across DRAM, SSD, and network — turning KV into a first-class storage tier addressable across the cluster. A KVCache-centric scheduler decides where each sequence's KV lives based on access pattern. Includes a *prediction-based early rejection* policy: when overloaded, reject incoming requests likely to violate SLO before consuming any compute. Layer-wise KV transfer (overlap with prefill compute) inherited from Splitwise/DistServe.

**Intel applicability:** HIGH at the architecture level. The "use the cluster's CPU + DRAM + SSD as a tiered KV store" idea is *exactly* what tahoma should be doing — Intel laptops have lots of fast DDR5/LPDDR5X system memory that's wasted when the iGPU is doing inference. Mooncake says: stash old KV blocks in system memory or SSD, page them back when needed. Particularly valuable on alpha where the iGPU's "VRAM" *is* shared system memory anyway, so paging is essentially free.

**Implementation cost:** LARGE for the full architecture. SMALL for the *first useful chunk*: an LRU-style spillover where evicted KV blocks go to system DRAM (already in tahoma's address space on iGPU systems!) instead of being dropped, and can be re-loaded on a later cache hit.

**Open hypothesis it generates for us:** On alpha (Lunar Lake, unified memory architecture), there is *no* memory hierarchy between iGPU "VRAM" and CPU DRAM — they're the same physical memory with different access paths. So Mooncake's "spill KV to DRAM" is a free operation on Intel iGPU. Hypothesis: a tahoma-on-Lunar-Lake worker can hold KV for multiple inactive sessions in system memory at zero throughput cost, allowing 10x more concurrent sessions than a naive per-iGPU-VRAM allocation budget would suggest.
