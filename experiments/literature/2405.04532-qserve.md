# QServe: W4A8KV4 Quantization and System Co-design (arXiv:2405.04532)

**Year / venue:** 2024, MLSys 2025.
**Headline claim:** 1.2-3.5x serving throughput vs TensorRT-LLM (Llama-3-8B and Qwen-72B on A100/L40S). 3x dollar-cost reduction.
**Mechanism:** The "QoQ" quantization recipe — *quattuor-octo-quattuor*, 4-bit weights, 8-bit activations, 4-bit KV. Two algorithmic ingredients: (1) *Progressive group quantization* — quantize weights to INT8 first (per-channel FP16 scales) then refine to INT4 (per-group scales over the INT8). This avoids the "register-level dequant" overhead that vanilla W4A8 incurs because the inner loop only does INT8-level dequant. (2) *SmoothAttention* — applies a SmoothQuant-style migration but on the attention path: shifts quantization difficulty from the KV cache to the queries (which aren't quantized), enabling clean INT4 KV. Paired with carefully scheduled fused attention kernels.

**Intel applicability:** MEDIUM-HIGH. The W4A8 algorithm is ideal for Intel Battlemage's XMX engines (which have an INT4-weight × INT8-activation fast path). The KV4 part requires a custom KV-cache layout in OV. SmoothAttention is a calibration step done offline at quantization time — fully portable.

**Implementation cost:** MEDIUM-LARGE. The OV side needs a W4A8 kernel (which exists for Battlemage) + INT4 KV-cache support (partial in OV 2025.x). The QoQ progressive quantization is just a calibration pipeline. The matmul kernel work is the bottleneck.

**Open hypothesis it generates for us:** On charlie, W4A8KV4 should give the best Pareto point between accuracy and throughput: ~1.5x decode tok/s vs W4A16 plus a ~3x serving-batch-size unlock from KV4. Concrete experiment: implement QoQ-style progressive quantization with NNCF, run Llama-3-8B on charlie at batch=1, 4, 16, compare to W4A16-AWQ. Hypothesis holds if QServe's curve is everywhere above AWQ's.
