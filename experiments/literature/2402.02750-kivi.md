# KIVI: Tuning-Free Asymmetric 2-bit KV Cache Quantization (arXiv:2402.02750)

**Year / venue:** 2024, ICML 2024.
**Headline claim:** 2.6x peak-memory reduction, 4x larger batch, 2.35-3.47x throughput on Llama / Falcon / Mistral with no fine-tuning. Negligible quality loss.
**Mechanism:** Empirical analysis of KV-cache statistics finds that *keys* have strong per-channel structure (specific channels are large across all tokens) while *values* have strong per-token structure (specific tokens have large values across channels). KIVI quantizes K *per-channel* and V *per-token*, both at 2 bits. The per-channel quantization for K requires a tiny scratch buffer per channel updated as new tokens arrive, but is otherwise trivial. The big win is the larger batch size enabled by the smaller cache.

**Intel applicability:** HIGH. KV-cache quantization is hardware-neutral — it's a memory-format change, plus a dequant operation right before each attention computation. OpenVINO 2024.x already supports INT8 KV-cache; adding INT2 with the asymmetric K/V layout is roughly a custom op or a script-side transform. Especially valuable on alpha (Lunar Lake) where 8GB shared memory is the tightest constraint.

**Implementation cost:** MEDIUM. Need to (a) implement per-channel quantization update for K (online min/max tracking), (b) implement per-token quantization for V, (c) modify the attention kernel to dequant on-the-fly. The dequant adds compute but saves bandwidth — net wins on memory-bound hardware.

**Open hypothesis it generates for us:** On alpha at 8K context, the KV-cache for Llama-3-8B-INT4 is approximately 256 MB (FP16 KV) — going to INT2 KV via KIVI cuts this to 32 MB, freeing memory for either a larger context or a draft model for spec-decode. Hypothesis: KIVI on alpha unlocks Llama-3-8B at 16K context with EAGLE-1 draft, which currently doesn't fit. This is a "feature unlock" hypothesis, not just a speedup.
