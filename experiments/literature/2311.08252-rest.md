# REST: Retrieval-Based Speculative Decoding (arXiv:2311.08252)

**Year / venue:** 2023, NAACL 2024.
**Headline claim:** 1.62x to 2.36x speedup on 7B and 13B models (single-batch), no training required, plug-and-play on any LM.
**Mechanism:** Replaces the draft model with a retrieval datastore. At each decode step: (a) take the longest suffix of the current context as a query, (b) fetch matching documents from a token-level datastore, (c) build a Trie of continuation candidates, prune low-frequency branches, (d) feed the resulting candidates to the LM as a tree-attention verification batch. The "draft" is essentially "what did the corpus say comes next after this exact suffix?" Wins big on code generation (boilerplate is highly predictable from suffix matches) and on RAG-style tasks where the prompt itself is in the datastore.

**Intel applicability:** HIGH. The retrieval is pure CPU work (suffix-array lookup, can be done in microseconds). The verification reuses standard tree-attention. No GPU kernels added at all. Particularly attractive for Intel because Intel CPUs are strong on this kind of cache-friendly random lookup.

**Implementation cost:** SMALL. Suffix-array datastore (~few hundred lines, can use existing `pyahocorasick` or `marisa-trie`), trie pruning, tree-attention mask construction. The bulk of the work is the offline datastore build (a few hours per corpus).

**Open hypothesis it generates for us:** REST should win disproportionately on code completion (the workload where Lunar Lake / Arrow Lake will most often be used in copilot scenarios). Concrete experiment: build a 1GB Python+TS code datastore, test on alpha with Qwen2.5-Coder-7B-INT4. Hypothesis: ≥ 2.5x decode speedup on HumanEval-style completion, vs ~1.3x on chat. If it holds, REST + Medusa-1 stacking might give 3-4x with minimal engineering.
