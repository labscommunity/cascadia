# FlexGen: High-Throughput Generative Inference with a Single GPU (arXiv:2303.06865)

**Year / venue:** 2023, ICML 2023.
**Headline claim:** Run OPT-175B on a single 16GB GPU at 1 tok/s with effective batch=144. 100x maximum throughput vs prior offloading systems.
**Mechanism:** Frames offloading as a constrained linear-programming problem: given (GPU mem, CPU mem, disk capacity, GPU compute, PCIe BW, CPU compute, disk BW), find the best schedule of (which layers' weights live where, which sequences' KV live where, what batch and block size to use). Solver picks the policy. Adds 4-bit weight + KV compression to make the math even more favorable. Reframes inference as latency-insensitive *throughput* optimization — for use cases like batch generation, evaluation, dataset distillation.

**Intel applicability:** HIGH for the *framework* (LP-based offloading planner is hardware-neutral and a great fit for tahoma's measured-resource topology). HIGH for the *workload assumption* — Intel laptops are throughput-tolerant for batch tasks. The *specific* implementation is GPU-centric and PyTorch-native; OV-native re-implementation is non-trivial.

**Implementation cost:** LARGE for a full FlexGen rewrite. SMALL to adopt the *LP formulation* in tahoma's master/placement: take the topology graph (already has bandwidth + latency edges) and solve a small LP for (which shard goes where, how big a batch/window). This is the right shape for tahoma's master to do anyway.

**Open hypothesis it generates for us:** A tahoma fleet has wildly heterogeneous resources (laptop iGPU, desktop dGPU, headless servers). A FlexGen-style LP planner could outperform hand-tuned placement by 1.3-2x on throughput-bound workloads (batch evaluation, RAG-doc indexing). Hypothesis: implementing even a coarse LP planner (3 decision variables: which-shard-where, batch-size, KV-precision) gives ≥30% throughput vs naive round-robin placement on a 3-machine heterogeneous fleet.
